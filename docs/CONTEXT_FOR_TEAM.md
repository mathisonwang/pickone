# 给团队的补充上下文（用户原始需求，勿改）

## 产品需求（用户原话提炼）
- 帮**选择困难患者**做选择的 Web App（只能做 web app）。
- 输入：自然语言，**语音或文字**。
- 用户既能**记录**"什么时候做了什么"，也能**提问**让 app 帮忙做选择。
- 选项复杂且**互相影响**。示例：
  今晚是去健身房跑步 / 去楼下那家火锅店 / 在家看电影。
  - 每个选项有自己的纠结点（通勤距离等）。
  - 若去健身房，路上能顺路买菜，且本周运动目标还差一次。
  - 若去火锅店，一个人吃有点尴尬，但老板娘很热情。
- 需**综合考虑**：例如用户平常每周想运动 3 次，但已经 4 天没动 → 优选运动，但同时要考虑通勤和预算。
- 有时选项**不是单一时刻**的：此刻的选择会影响接下来的安排 → 需要推演后果。

## 产品三原则（已与用户确认）
1. 三张牌：GO（就它了）/ SWITCH（你没想到的第三种组合）/ DROP（识别"伪选择"，别纠结了）。
2. 每次输出带置信度 + 最不确定项 + 一个具体追问（可解释 = 可信 = 敢用）。
3. 后悔闭环：事后回收满意度，让推荐越用越准（这是护城河）。

## 为什么必须用 mxagent（比赛叙事，README/演示要用）
- `--level` 递归分解 → 层级"决策专案组"，每个选项一条时间线子 agent 推演未来 48h。
- `--snapshot` + `<snapshot>.d/agents/*.jsonl` → 长期记忆 + 每步决策可审计回放（可解释性数据来源）。
- `--censor` → 健康/预算/安全硬约束在**生成前**拦截。
- `--result_check` → 自动质检理由是否自洽。
- `agent2tool` / `--as_mcp` → 抽取器/推演器/解释器作为可复用 agent 能力分层组合。
- `--cost_limit` → 每次决策成本透明（可展示"这次建议花了 ¥0.03"）。
