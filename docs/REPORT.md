## 1. 项目概述

**一句话定位：PickOne 是一个帮选择困难的人做决定的可解释决策引擎，不是聊天机器人。**

用户用自然语言（文字或语音）说出纠结——"今晚是去健身房跑步，还是去楼下那家火锅店，还是在家看电影？"——系统综合**用户长期档案**、**每个选项的未来 48 小时推演**、**硬约束校验**，最后**只给一个结论**和它的好处。

标题句 **Attention is what we save.** 借用了《Attention Is All You Need》的句式。Transformer 把注意力机制变成模型的核心能力，我们想反过来：**把人的注意力省下来**。这不是文案游戏，它直接决定技术选型——要省下人的注意力，系统就必须**敢自己推演**、**敢记住你**、**敢说"这条我不确定"**，分别对应 mxagent 的层级递归委派、snapshot 长期记忆与可审计决策轨迹（详见第 5 节）。

## 2. 痛点分析

### 2.1 成本不在"选错"，在"纠结本身"

选择困难最贵的成本不是选错，是**你为一个 5% 差距的选项耗掉的那半小时**。多数"选错"其实没那么糟，不选才最消耗人。视频解说词里有一句直白的话："真正累的，纠结本身。

### 2.2 三个通用问答工具都不处理的事

| # | 难点 | 例子 |
|---|---|---|
| 1 | **选项互相影响** | "一个人吃火锅有点尴尬"——选项不是独立条目，是一张互相咬合的网 |
| 2 | **需要考虑长期后果** | 此刻的选择会改变未来 48 小时的精神状态、后天的安排 |
| 3 | **需要考虑个人节律** | "每周想运动 3 次、已经 4 天没动"这种只有你自己知道的事 |

ChatGPT 类工具对这三个都是**无状态**的：它不记你、不推演后果、不给结论（只列优缺点）。问它"我该选 A 还是 B"，它列一堆优缺点然后说"最终取决于你"——**又把纠结原样还给了用户**。

### 2.3 市面产品在努力让你更纠结

纠结 = 停留时长 = 广告库存。给三张牌让你比、给对比表让你核对每一维、给"查看更多选项"让你继续下滑——这些设计都在**消耗**用户的决策预算。**PickOne 选了另一条路：把纠结吃掉，而不是还给你。**

## 3. 解决方案：只给一个结论

### 3.1 产品形态

用户输入一句话（打字或语音），等待 30~60 秒，得到：

```
┌─────────────────────────────────────────┐
│  置信度环  69%   大方向定了，还有一点小变量   │
│  最不确定：健身房跑步 的开始时间未知       │
├─────────────────────────────────────────┤
│  💬 想清楚了，去就行。                    │
├─────────────────────────────────────────┤
│  ┌───────────────────────────────────┐  │
│  │  GO · 就它了                      │  │
│  │  就它了：健身房跑步                │  │
│  │  · 你已经 4 天没运动了             │  │
│  │  · 本周运动目标 3 次，目前只完成 0 次│  │
│  │  · 节律缺口这项拿到 10.0/10        │  │
│  │  · 花费约 25 元，钱包压力小         │  │
│  └───────────────────────────────────┘  │
│  它强在哪：7 个维度条形图（只有它一个）    │
│  🔍 幕后：AI 是怎么想的（可展开推理树）    │
│  🌙 昨晚去了吗？感觉如何？（后悔闭环打卡）  │
└─────────────────────────────────────────┘
```

**没有第二张牌，没有对比表排名，没有"其他选项"入口。**

### 3.2 为什么"只给一个"——产品最重要的一次判断

我们最早做的是三张牌（主推、第三种可能、还有"这个不值得纠结"），后来**把它砍了**：

- **展示多个选项本身就是内耗。** 给三张牌，用户会开始比牌；给对比表，用户会去核对每一维。我们做了半分钟推演，最后又把纠结原样还给了用户——那推演就白做了。
- **信息不全也无所谓，随便选一个。** 抽不出选项就从原话里抓一个，再不行给"先出门走走"。**选择困难的解药常常不是"想清楚"，是"承认想不清楚，然后动起来"。**
- **只讲优点，不提缺点。** 说"通勤是硬伤"除了让人犹豫，没有任何作用。系统内部照常用 7 个维度打分、照常跑硬约束闸门，但**只把结论和它的好处告诉用户**。

代码层面这是硬约束：`Decision.cards` 恒为长度 1 的 `[GO]`，不产出 SWITCH / DROP（`engine/explainer.py`）。`tests/test_engine.py` 有专项用例 `test_only_one_card_even_when_gap_small`——**即使前两名分差小于阈值，也只给一张牌**。

### 3.3 置信度与收尾一句

每次输出必带 `confidence`（0~1）、`most_uncertain`（最影响结论的未知项）、`ask_user`（一句劝退纠结的收尾）。**低置信度不是缺陷，是诚实。** 但我们**不把不确定性转嫁给用户**——不说"你补这条信息我立刻改答案"（那是在诱导二次纠结），而是说"信息不多也能定，先去试试"。

**可解释 = 可信 = 敢用；而敢替你拍板 = 真的帮你省下了注意力。**

## 4. 技术架构

### 4.1 五段决策流程

```
 用户输入（文字/语音）  web/index.html + app.js（原生 JS，无构建无 CDN）
        │  POST /api/advise
        ▼
 server/app.py（starlette + uvicorn）后台线程执行 + 轮询 /api/decision/{id}
        │  engine_bridge（REAL / stub 自动切换）
        ▼
╔═══════════════════════════════════════════════════════════════╗
║  engine/ — mxagent 决策引擎                                    ║
║   ① Extractor   LLM 结构化抽取 → DecisionRequest              ║
║                 （选项/纠结点/硬约束/缺失信息）                 ║
║   ② Timeline    mxagent --level 2 层级委派                     ║
║                 → 每选项推演未来 48h 连锁后果                   ║
║   ③ Scorer      纯 Python 确定性 7 维加权打分                  ║
║                 → 各维度分 + 总分（LLM 不算数，同输入同输出）    ║
║   ④ Censor      硬约束闸门（预算/截止时间）                    ║
║                 → 违规选项 feasible=false，生成前拦截           ║
║   ⑤ Explainer   唯一 GO 牌 + 只讲优点 + 置信度 + 推理树        ║
║                                                               ║
║        ▼  GO · 就它了（只有这一张）                            ║
╚═══════════════════════════════════════════════════════════════╝
        │
        ▼
 data/（decisions / profiles / feedback.jsonl / snapshots）
```

| 段 | 模块 | LLM 参与 |
|---|---|---|
| ① Extractor | `engine/extractor.py` | ✅ LLM 抽取 + 正则兜底 |
| ② Timeline | `engine/timeline.py` | ✅ `--level 2` 委派 |
| ③ Scorer | `engine/scorer.py` | ❌ **纯 Python 确定性** |
| ④ Censor | `engine/censor.py` | ❌ 纯函数 |
| ⑤ Explainer | `engine/explainer.py` | ❌ 确定性生成 |

### 4.2 七个打分维度

| 维度 | 含义 | 默认权重 |
|---|---|---|
| `rhythm` | 生活节律缺口（每周想运动 3 次、已 4 天没动 → 高分） | 0.22 |
| `social` | 社交价值（见朋友、陪伴） | 0.18 |
| `commute` | 通勤/时间成本（越低越好，取负） | 0.16 |
| `cost` | 花费（越低越好） | 0.10 |
| `pleasure` | 愉悦度/期待感 | 0.16 |
| `health` | 健康与体力（疲劳、天气、身体状况） | 0.12 |
| `future` | 对未来 48h 安排的连锁影响（由 Timeline 给出） | 0.06 |

每维 0~10 分，加权求和 → `total`。权重来自用户档案，可被满意度反馈调整。

### 4.3 两条产品修正（工程细节里的产品判断）

1. **`commute` / `cost` 设"零成本区"**：通勤 `<=15min`、花费 `<=30元` 一律视为同等便利，不再线性加分。否则"什么都不做"（0 分钟通勤、0 花费）会永远压过"步行 5 分钟、人均 80"——**躺平永远赢**。
2. **`rhythm` 缺口到阈值（`>=9`）时给运动类选项硬性加分（+0.8）**。一周该动 3 次却 4 天没动是长期目标，"零通勤零花费"是短期便利；线性加权下短期便利很容易压过长期目标，导致系统自相矛盾（说"你 4 天没运动了"却推荐在家看电影）。阈值判断更接近真实决策心理：**欠账太多时优先补课**。

## 5. 为什么必须用 mxagent

> **通用框架给你"能跑"，mxagent 给我们"可解释、可审计、可降级、可复用"。**
> 而这四样，正是决策类产品能不能被人信任的分水岭。

下面每一项都对应产品里的一个具体画面，不是抽象优势。

### 5.1 `--level 2` 层级递归推演 → 每个选项一条时间线

```
mxagent --task "..." --level 2 --snapshot data/snapshots/<decision_id>/
```

编排 agent 把"推演每个选项的后果"委派给子 agent，**每个选项一条独立时间线**，推演到未来 48 小时的连锁影响。这是前端等待页六步（理解 → 推演今晚 → 推演未来48h → 权衡节律与通勤 → 安全校验 → 生成建议）的来源。

**对照 LangGraph**：LangGraph 给你编排原语，但**不给你"层级决策专案组"的语义**——子 agent 生命周期、trace 格式、层级快照都要自己造。

### 5.2 snapshot 长期记忆 + per-agent 可审计轨迹 → 可解释性的数据来源

```
<snapshot>.d/agents/*.jsonl     # 每个 agent 的完整决策轨迹
```

- **长期记忆**：档案（运动频次、偏好、约束、历史活动）跨决策持久化，这是"新用户 vs 老用户给出不同建议"的硬件基础。
- **可审计回放**：每次层级推演的每一步都落盘成 jsonl，前端「🔍 幕后：AI 是怎么想的」折叠面板直接渲染成树。
- **监管价值**：被问"你为什么推荐这个"，我们能把它走过的路一步一步摊开。

**对照 LangGraph**：LangGraph 的 checkpointer 是给**图状态**用的，不是给"每个子 agent 的推理轨迹可回放"用的。

### 5.3 `--censor` 工具调用前闸门 → 硬约束在**生成前**拦截

```
--custom_tools censor.py    # @add_censor 拦截工具调用
```

健康 / 预算 / 时间三类硬约束，**在生成前**拦截。被拦选项 `feasible=false`，**structurally 当不上 GO**，并写入 `blocked` / `blocked_reason`。实测拦截实例（真实 LLM 模式，`data/decisions/dec-20260927-114448-ce970b.json`）：

> 「按开始 21:30出发 + 180 分钟 + 单程通勤 60 分钟推算，到家约 01:30，晚于截止 22:30」

**对照 LangGraph**：自己拼框架只能在**生成后**过滤——"生成完了再删掉不合规选项"和"不合规选项根本没被生成出来"是两回事。**后者才是安全，前者是补救。**

### 5.4 能力复用与成本透明

- **`agent2tool` / `--as_mcp`**：抽取器 / 推演器 / 解释器作为**可复用 agent 能力**分层组合，不是三个耦合的 Python 函数。`engine/agents/` 下沉淀了 `extractor.yaml` / `timeline.yaml` / `explainer.yaml` 三个 agent 配置，换模型、换抽取策略不动推演器。
- **`--cost_limit`**：每次决策成本透明。**`--result_check`**：自动校验输出理由是否自洽，失败自动重试（重试 1 次，再失败走降级）。

### 5.5 能力映射总表

| mxagent 能力 | 在产品里的体现 | 对应演示画面 |
|---|---|---|
| `--level 2` 层级递归委派 | 每个选项一条独立时间线，推演 48h 连锁后果 | 等待页六步动画 |
| snapshot 长期记忆 + per-agent 可审计轨迹 | "它记得你"（4 天没运动）+ 可解释性的数据来源 | 新用户 vs 老用户；推理树 |
| `--censor` 工具调用前闸门 | 硬约束在生成结论前拦截 | 安全校验步骤 |
| `agent2tool` / `--as_mcp` | 抽取器/推演器/解释器作为可复用 agent 能力 | 架构分层 |
| `--cost_limit` | 每次决策成本透明 | 商业展示 |
| `MXAGENT_BIN` 降级开关 | 指向不存在的可执行文件 → 走启发式，产品仍可用 | 韧性演示 |

## 6. 演示效果与实测数据

### 6.1 主案例

**输入**（`demo/cases.json` 第一条，135 字）：

> 今晚好纠结：方案一去健身房跑步，单程通勤40分钟，年卡折合每次25块钱，但最近工作太累；方案二去楼下那家火锅店，步行5分钟，人均80，一个人吃又有点尴尬；方案三在家看电影，零通勤零花费，但今晚首映怕被剧透。我预算今晚不超过100块，而且明天早上7点要起床上班，选哪个好？

信息密度是演示重点：三个选项、各自通勤与预算、明早要起床上班，还有两条**选项之间的相互影响**——一个人吃火锅有点尴尬，今晚首映怕被剧透。

### 6.2 "AI 懂你"的硬证据：同一问题，两个人问，答案不一样

2026-09-28 实测（`engine/cli.py --case workout_vs_hotpot_vs_movie`）：

| 档案 | GO 结论 | 置信度 | 理由 |
|---|---|---|---|
| **新用户**（空档案） | 就它了：在家看电影 | 0.43 | 单程通勤只要 0 分钟 / 花费约 0 元 / 体力负担轻（10.0/10） |
| **3 周老用户**（veteran） | **就它了：健身房跑步** | 0.69 | 你已经 4 天没运动了 / 本周运动目标 3 次，目前只完成 0 次 / 节律缺口这项拿到 10.0/10 / 花费约 25 元 |

老用户档案有 5 条长期事实（"楼下火锅店的老板娘很热情"、"不吃辣"、"预算敏感，单晚超过 100 会犹豫"、"偏好步行 15 分钟能到的地方"、"每周想运动 3 次"）和 9 条历史活动（最近一次运动在 4 天前）。

**同样一句话，两个人问，答案不一样。这不是写死的 if-else**，是 `rhythm` 维度真的算了"每周想运动 3 次、已 4 天没动"的缺口，`social` 维度真的读了"楼下火锅店的老板娘很热情"这条事实。

> 注：新用户在快速模式（`use_llm=false`）下 GO 为"去楼下那家火锅店"，理由是"单程通勤只要 5 分钟 / 花费约 80 元"——同样是通用表述，与老用户的档案证据型理由形成对比。**具体结论以实际运行为准。**

### 6.3 硬约束拦截实例

输入："今晚21:30出发去健身房跑步，单程60分钟，预计练2个小时；或者去楼下那家火锅店，19:00开始吃90分钟，单程5分钟。我22:30之前必须到家。" 实测输出（真实 LLM，17.3s）：

```
GO = 就它了：去楼下那家火锅店
blocked = [{'option_id': 'opt1',
            'reason': '按开始 21:30出发 + 120 分钟 + 单程通勤 60 分钟推算，
                       到家约 01:30，晚于截止 22:30'}]
scored = [('去楼下那家火锅店', 6.22, True), ('去健身房跑步', 5.90, False)]
```

被拦选项**没有成为 GO**，符合"安全闸门优先"。

### 6.4 幕后推理树（不是黑盒）

```
你在今晚的 3 个选项间纠结，先理清约束与节律缺口
  ├─ Extractor    · LLM 结构化抽取完成
  ├─ Timeline     · 对每个选项推演到未来 48 小时的连锁后果
  ├─ Scorer       · 纯 Python 确定性加权打分（同输入同输出）
  ├─ Censor       · 未发现违反硬约束的选项
  └─ Explainer    · 只给一个结论（GO），附它的优点与收尾一句
```

Timeline 节点的 summary 来自 `<snapshot>.d/agents/*.jsonl` 里子 agent 的**真实输出**，不是占位文案。一条真实的 48h 推演：

```
今晚  -1  跑步后身体疲惫，洗澡休息可能较晚入睡
明天  +1  肌肉略有酸痛，但精神状态较好，工作效率尚可
后天  +1  身体基本恢复，运动带来的正向状态持续
future_score = 7    risk = 通勤40分钟耗时较长，可能压缩休息时间
```

### 6.5 性能实测

| 模式 | 实测耗时 | 说明 |
|---|---|---|
| 完整 LLM 链路（veteran，主案例） | **61.1s** | `engine/cli.py` 实测，含抽取 + 推演 |
| 完整 LLM 链路（新用户，主案例） | **38.3s** | 同上 |
| 完整 LLM 链路（健身房硬约束案例） | **17.3s** | 选项信息更完整，推演更快 |
| 快速模式（`use_llm=false`） | **< 0.1s** | 纯启发式，CLI 实测 0.027~0.046s |
| 引擎自测记录的链路分解 | 抽取 ~17s + 推演 ~30s ≈ 50s | `engine/SELFTEST.md` |

后端有 150s 硬超时看门狗，前端等待超过 60s 自动出现「⚡ 太久了，先用快速模式看看」按钮。**LLM 是共享资源（本机 llama-server `--parallel 1`），随时可能被别人占满，双模式是必需品。**

### 6.6 本地 ASR

faster-whisper `small`（461MB，CPU int8，4 线程），完全离线：

```
$ python asr/transcribe.py asr/.tmp/e1_workout.webm --lang zh
[asr] model loaded in 0.59s (device=cpu, compute=int8, threads=4)
[asr] ok: 25 chars in 1.61s (attempt 1)
今晚是去健身房跑步,还是去吃火锅,或者在家看电影。
```

**为什么做离线版**：你说的纠结是很私密的事，不该为了转个文字就上传到云端。后端 `/api/asr` 契约写死：识别失败返回 `{"text":"","unavailable":true}`，**绝不 500**。诚实说明：`small` 对口语有偏差，实测「在健身房练基本功」被误识为「地链机本功」，演示只用实测识别准确的两个音频。**我们知道自己的边界在哪。**

### 6.7 演示视频

`pickone_demo.mp4`（仓库根目录，另附 `pickone_demo_720p.mp4` 上传版）：时长 **67.700s**，1440x900 @ 30fps（2031 帧），H.264 + AAC 192kbps，5,754,614 bytes。字幕已烧录（ASS + Noto Sans CJK SC），22 句中文解说（`zh-CN-YunjianNeural`，句间间隔 0.2s，语音总长 41.956s 由 ffprobe 逐句实测），BGM 为 ffmpeg 正弦合成 pad（CC0 零版权），音量 0.14 + sidechain ducking。**画面 100% 真实录屏**（8 幕 + 3 个补充片段，无 Ken Burns、无尾帧定格）。**17 段静音全部 ≤ 3.5s**（ffmpeg silencedetect 实测，最长 3.285s）——为此对长静音窗口做了分段线性变速（视频/音频/字幕共用同一张映射表，从机制上保证三者同步）。

## 7. 工程亮点

### 7.1 LLM 不算数：对"AI 胡说八道"的工程防御

**LLM 只做理解与推演，算术一律在 Python。** 分数、排名、通勤成本换算全部 `scorer.py` 确定性计算。LLM 输出的数值只作为"主观权重估计"，且必须 clamp 到合法区间。实测验证（同输入跑两次，快速模式）：

```
第 1 次：[('去楼下那家火锅店', 5.56), ('去健身房跑步', 5.29), ('在家看电影', 4.72)]
第 2 次：[('去楼下那家火锅店', 5.56), ('去健身房跑步', 5.29), ('在家看电影', 4.72)]
```

`tests/test_engine.py` 有 `test_deterministic_same_input_same_output` 专项用例；`scorer.py` 是纯函数（无随机、无时间依赖、无 LLM）。

### 7.2 降级韧性：四层降级，每层都是产品功能

| 层 | 触发条件 | 行为 |
|---|---|---|
| 1 | LLM 超时 / 报错 | 引擎启发式兜底 + `degraded: true` |
| 2 | 后端 150s 硬超时 | 自动转降级结果并标注原因 |
| 3 | 前端等待 > 60s | 出现「⚡ 太久了，先用快速模式看看」按钮 |
| 4 | `?mock=1` | 纯离线演示模式，**零网络请求，断网可演** |

**硬性验收标准**：`MXAGENT_BIN=/nonexistent/mxagent` 时，服务必须返回合法 Decision 且 `degraded=true`，**绝不 500**。实测通过。而且我们**不藏**——降级时前端明确显示"⚠️ AI 引擎暂时不可用，本次为快速启发式结果"，因为**伪装成高置信的低质量建议，比承认降级危险得多**。

### 7.3 结构化输出容错与可解释性

task 里要求"只输出 JSON"，Python 侧多层容错：剥 ```json 围栏 → 正则抓第一个 `{...}` → 修复终端折行污染（`"start_hint"` 被折成 `"sta rt_hint"`）→ jsonschema 校验 → 失败重试 1 次 → 再失败走降级。

`reasoning_tree` 完整保留层级推演过程，前端直接渲染成树，数据来源是 mxagent 的 snapshot 落盘，每步决策可审计、可回放。**监管问"你为什么推荐这个"，我们能把它走过的路一步一步摊开。**

### 7.4 后悔闭环：越用越准

每次决策落库 `decision_id`，事后回收 `{chosen, went, satisfaction 1-5, note}`。`profile.apply_feedback()` 按"实际选择 vs 推荐"与满意度微调维度权重（学习率 0.05，权重和归一化，单维限制在 [0.05, 0.35]）。

实测打卡一次（满意度 5/5，选了"去健身房跑步"）：

```
before: rhythm 0.22, social 0.18, commute 0.16, cost 0.10, pleasure 0.16, health 0.12, future 0.06
after : rhythm 0.2082, social 0.1823, commute 0.1667, cost 0.1042, pleasure 0.1823, health 0.1042, future 0.0521
facts += ['曾选择「去健身房跑步」，满意度 5/5']
```

档案变化**必须可查询**（前端「👤 我的档案」页实时展示），用户可一键重置。**数据主权在用户手里，这才叫可信。**

## 8. 商业价值

**短期：工具订阅。** 选择困难的痛点是高频的（每天好几个决定），付费意愿在"省下的纠结时间"。我们不卖广告，因为**我们的产品目标是减少纠结时长，不是增加停留时长**——这两个 KPI 在推荐系统里通常冲突，我们选了前者。

**中期：数据护城河。** 后悔闭环攒的档案是**迁移成本**。用户换产品要重新养一个"认识自己"的系统，这个成本比订阅费高得多。**模型谁都能调，"我认识你"这件事，竞品要从零开始攒。** 这是唯一能对抗"换个模型就重来"的壁垒。

**长期：决策基础设施。** 单结论 + 置信度 + 可审计轨迹这套范式，可平移到医疗、教育、投资等**高 stakes 场景**——那些场景里"可解释"不是加分项，是准入证。

| 阶段 | 形态 | 关键指标 |
|---|---|---|
| 现在 | 本地 Web App（本机 / 局域网） | 决策质量、可解释性、降级韧性 |
| 近期 | 容器化部署 + 多用户隔离 | 并发决策、档案隔离 |
| 中期 | 移动端 + 语音优先 | 输入摩擦、日活决策数 |
| 远期 | 垂直场景决策 API（`--as_mcp`） | B 端接入数 |

## 10. 已知限制与未来规划

### 10.1 已知限制（诚实版）

| 限制 | 说明 |
|---|---|
| LLM 是共享资源 | 本机 llama-server `--parallel 1`，随时可能被别人占满；完整推演 17~61s（实测），设计预期 60~180s |
| `--level 2` 经常不产生子 agent | LLM 对"分别推演每个选项"倾向自己直接答完，snapshot 里只有根 `Agent.jsonl`。已用"LLM 真实返回的后果合成节点"兜底，视觉上仍是有内容的树，但层级深度不如预期 |
| ASR 中文准确率依赖音频质量 | `small` 对"健身房练基本功"误识为"地链机本功"；换 `medium`（约 1.5GB）更准但下载慢 |
| 浏览器语音兼容性 | Web Speech API 在 Firefox 不支持（按钮置灰），Chrome / Edge 可用；离线 ASR 走 `/api/asr`，不受浏览器限制 |
| 公网映射当前不可用 | 文档记载的 `http://106.13.186.155:8051` 实测返回另一个应用的页面，演示一律以 `http://127.0.0.1:8888` 或局域网 IP 为准 |
| `data/snapshots/` 会持续增长 | 每次 LLM 决策都落一个 snapshot 目录，长期运行需要清理策略（未实现，避免误删） |
| 前端未做真实浏览器截图级验证 | 动画、375px 溢出仅代码级审查 + Node 冒烟 |

### 10.2 未来规划

**产品侧**：① 稳定拿到多层推演——在 task 里更强硬地要求"为每个选项启动一个子 agent"，让 `--level 2` 真正产出 N 条并行时间线；② `explainer.yaml` 的 LLM 润色能力接线（当前刻意保持确定性生成以保证可单测、降级不崩）；③ 探索"一次只问一个最关键问题"的轻量澄清形态。

**工程侧**：④ snapshot 清理策略（按决策时间 + 引用计数安全回收）；⑤ 真实浏览器截图级验证（Playwright / CDP 动画与响应式断言）；⑥ 容器化 + 多用户隔离。

**商业侧**：⑦ 基于 `--as_mcp` 把"单结论 + 置信度 + 可审计轨迹"包装成 B 端决策 API，优先切入医疗 / 教育选择这类"可解释是准入证"的场景。

## 结语

PickOne 做的事情可以用三句话概括：

1. **它给结论。** 只给一个，只讲优点，连缺点都不说——因为展示多个选项本身就是内耗。
2. **它认识你。** 你的运动频次、通勤耐受、预算约束在档案里，同样问题不同人不同答案。
3. **它不是黑盒。** 每一步推演落盘可回放，每一步算术都在 Python 里确定性完成。

**通用模型是无状态的，我们是有状态、有记忆、有审计轨迹的。Attention is what we save.** —— 这个标题不只是文案，它决定了我们所有的技术选型。
